**Critical instrumentation issue:** `get_app_permissions` also says `not_installed` for GitHub and Context7 even though plugin search identifies them as installed and their actions are currently callable. Therefore a `not_installed` permissions response is **not a reliable installation diagnostic**, and earlier conclusions based on it were overstated.

**Private plugins are not universally inaccessible**, since Asterion Continuity's personal skill loads successfully. Asterion Control's absence correlates with its authenticated MCP component, not simply the fact that it is private.

## Manifest comparison
Asterion Control v1.7.4 has:
- Root `plugin.json` with Agent Plugins 1.0 schema.
- Root `mcp.json` with Agent Plugins 1.0 schema, one `streamable-http` MCP entry, public HTTPS endpoint, and `extensions.com.openai.auth.type=oauth` with dynamic client registration and `asterion.control` scope.
- Legacy `.codex-plugin/plugin.json` with `mcpServers: "./.mcp.json"`.
- Valid `skills/control/SKILL.md` YAML front matter.
- No required SDK `apps` reference in either manifest, as of v1.7.4. The unused `.app.json` archive artifact is preserved but not referenced.

OpenAI's published plugin packaging docs explicitly support this layout and direct OAuth MCP configuration: https://developers.openai.com/plugins/build/plugins. Agent Plugins specification: https://agent-plugins.org/specification. There is **no observed missing root mcp.json or invalid absolute legacy reference** in this version.

## Account/platform constraint to verify — not a proven sole cause
OpenAI's [custom MCP documentation](https://help.openai.com/en/articles/12584461-connecting-custom-mcp-servers-in-chatgpt) states that full custom MCP support, notably write/modify access, is offered for Business and Enterprise/Edu, while even Pro users have read/fetch restrictions. The plugin directory may be accessible on other plans, but access to individual MCP capabilities is plan/role/surface-dependent: https://help.openai.com/en/articles/20001256-plugins-in-chatgpt. This is a **plausible limitation** for the requested full write-capable integration, not conclusive diagnosis of the specific host loading failure. User already tested Work and it failed: do not suggest the same workaround again.

To settle native tool loading conclusively, obtain a server-side plugin activation/authorization failure reason from ChatGPT's plugin host or workspace availability signal. In the meantime, use the proven existing authenticated Control transport for real projects and preserve the canonical full-MCP server for any future supported native connection.
